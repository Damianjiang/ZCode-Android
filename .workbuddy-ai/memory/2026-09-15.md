### 根因与改动（按文件）

**ConversationV4.kt**
- `setRows` 原来每次都对整张 rows 做 `row.copy(version=...)`，而流式文本每个 token 都触发一次
  → O(n) 分配 / token。改为：`publishRows(newRows, structureChanged)` 不再拷贝行；
  `_structureVersion`（增删行才递增）与 `_contentVersion`（内容变化递增）分离。
- 新增流式 delta 缓冲：`DeltaBuffer`（rowId → path → StringBuilder）+ `pendingDeltas`，
  `scheduleDeltaFlush()` 每 60ms 批量提交一次（`flushPendingDeltas`），
  结构操作前先 flush 保证追加顺序。
- `subscribeConversation` 超时 10s → `SUBSCRIBE_TIMEOUT_MS = 45_000` 并重试一次，返回 Boolean。
- 新增 `HistoryState { LOADING, READY, EMPTY, FAILED }` + `retryHistory()`，
  订阅失败时降级到 `loadRows` 兜底，不再静默空白。
- `applySnapshot`：window 为空时不再清空已加载的更早历史。
- 翻页游标改为「当前已加载最早一行 rowId」，新增 `hasOlderHistory`（结合 `hasMore`）。
- `sendText` 补回 `requestedDelivery` 字段（此前「排队」按钮在协议层完全无效）。
- 新增 `rowsLock` 保护 rows 的读改写。

**RelayClient.kt**
- 每个 payload 一条 `scope.launch { _payloads.emit() }` → 改为无界 `Channel` + 单一消费者
  `inboundDispatcher` 按序转发；buffer 64 → 256。

- `addEventListener` 的 `cancelled` 标志拆成 `sent` / `disposed`，注销幂等。

**ZemoteLogger.kt**
- 每条日志 O(1000) 快照 + Compose 状态写入 → 约 300ms 批量发布；
  `SimpleDateFormat` → `java.time.format.DateTimeFormatter`（线程安全）。

- onLog 不再同时写 debug + info（日志翻倍）。

## 第二轮：对照官方 bundle 核对协议（追加修复）

官方 Web 客户端逆向产物在 `zcode_downloaded/remote/v4/assets/index-nOVzQNKW.js`
（另一个副本在根目录 `bundle.js`）。用它逐条验证了协议假设，并发现两个新缺陷：

**验证结论（原假设成立）**
- `sendText` schema：`{text, attachments?, requestedDelivery?: ['startNow','queue','guide'], ...}`，
  且官方调用点是 `...n?.requestedDelivery ? {requestedDelivery: ...} : {}` —— 只在存在时下发。
- 翻页：官方传 `beforeRowId = window[0].rowId`（当前已加载最早一行）→ 我改的方向正确，
  原实现传服务端 `firstRowId` 是错的。
- `wb()` 判定：`firstRowId === null → false`，否则 `window[0].rowId > firstRowId`。
- `rowsRange` 响应：`{rows, atSeq, atLogEpoch, hasMore}`（**没有 totalCount**）。
- `row.appended` 会 `firstRowId: firstRowId ?? row.rowId`；`row.removed` 的
  `fromRowId <= firstRowId → totalCount=0, firstRowId=null`；`row.delta` 用同款字段级拼接。

**新发现并修复**
1. **`sendText` 返回值必须校验**：官方 `status !== 'accepted'` 即抛错，成功状态集合为
   `{accepted, duplicate, noop}`。本 App 之前完全忽略返回值 → 消息被拒时输入框已清空、
   界面无反馈。已引入 `SendOutcome{Accepted, Rejected}`，UI 侧被拒时恢复输入与附件并提示。
2. **队列冲突**：`guard.heldQueueConfirmationStale` 需要客户端明确处置
   （`clearQueueAndSend` / `keepQueueAndSend` + `expectedHeldQueueItemIds`）。
   已自动按 `keepQueueAndSend` 重试一次（不丢用户排队消息）。
3. **分页跨纪元脏页**：官方校验 `atLogEpoch === snapshot.logEpoch`，不一致整页丢弃。已补。

新增字符串资源 `send_rejected`（zh/en 双语）。

## 第四轮：UI卡顿 / 历史加载失败 / 渲染慢 / 行为不符 / bridge 取信息慢（v1.9.2）

用户一次性提了 5 类问题，逐项定位根因后全部修复，`assembleDebug` 已通过。

**1）UI 卡顿**
- 根因：`ChatScreen` 顶层订阅 13 个 StateFlow，其中 `usage` 随每个 `state.updated`
  补丁更新（~16 次/秒），每次都把整页（含 MessageTimeline + 所有可见消息）重组。
- 修复：新建 `ComposerSection`，把 `convConfig/usage/modelOptions/stopWorkId/
  followupMode/queueItems/autoDrain` 的订阅下沉进去；ChatScreen 只留页面骨架需要的
  低频状态。`loadAttachment` 改用 `rememberUpdatedState` + `remember` 固定实例；
  `autoFollow` 改显式 `MutableState` 以 remember 出稳定 setter。

**2）历史持续加载失败**
- 根因 A：`loadRows` 软失败分支只 `log` 后 `return _rows.value`，**从不抛异常**，
  而调用方全靠 `runCatching{}.onFailure{ _historyState = FAILED }` → FAILED 永不设置，
  永久停在 LOADING 转圈、连重试按钮都没有。新增 `markHistoryLoadFailed()`。
- 根因 B：`retryHistory` 只看 subscribe 返回值，订阅成功但快照没来同样永久 LOADING。
  加 3s 快照等待窗口，仍未填充就主动拉一次。
- 根因 C：三条兜底路径（订阅失败回退 / 2s 安全网 / 手动重试）并发重复加载。
  用 `historyLoadMutex` 串行化 + 初始加载前检查「是否已有人填过历史」。
- 顺带兼容 `{rows:[...]}` 与 `{rows:{rows:[...]}}` 两种响应形状（旧实现遇到后者
  读不到 hasMore/atLogEpoch，翻页会提前终止）。

**3）渲染慢**
- `mergeRow` 由 `associateBy + sortedBy`（O(n log n) + O(n) 分配）改为按 rowId
  二分定位 + 就地替换/插入。流式期间工具行会被反复 upsert，这是主要来源。
  保留「内容一致则复用旧实例」的不变量。
- `row.appended` 增加乱序/重放检测（`rowId <= 末行` → 退化为 upsert），
  避免 resync 重放产生重复 rowId 让 LazyColumn 重复 key。

**4）行为不符预期**
- `DisplayItem.ToolGroup.key` 从 `g-首行-末行` 改为 `g-首行`：组增长时 key 变化会让
  LazyColumn 销毁重建整张「执行过程」卡片（FadeInContainer 重新淡入 + expanded 重置）。
- `hasMore` 从普通 var 改为可观察的 `hasMoreFlow: StateFlow<Boolean>`，
  时间线订阅后再算 `hasOlderHistory`（旧写法在组合中读普通 var 不产生订阅）。
- `flushPendingDeltas` 不再无条件清空 `pendingDeltas`：只移除真正落到行上的，
  避免「行还没到」的 delta 被丢（表现为 AI 回复少一段字）；`row.appended` 落地时
  就地补上该行已缓冲的 delta。

**5）bridge 取信息慢**
- 主因：`RelayClient.payloads` 是 `extraBufferCapacity=256`、默认 SUSPEND 的 SharedFlow，
  而 `BridgeSession` 的收集协程在 collect 体内**同步**做 Base64 解码（单帧最大 512KB）
  + CRC32 + value-list 解码。一条多兆响应能让它几百毫秒回不到 collect，缓冲区拖满后
  emit 挂起 → **整条 relay 入站管线停摆**。给 `BridgeSession` 与 `ZemoteClient` 的
  payload 收集各加 `.buffer(Channel.UNLIMITED)` 解耦。
- `RpcFrameTransport.acceptPayload`：先查重再 Base64 解码（重传不再白解码）；
  用 `received` 计数器替代 `fragments.all{}` 整数组扫描；补分片下标越界与
  messageBytes 上限校验；`assemblies` 换 `ConcurrentHashMap`。
- `purgeStaleFragments` 节流到 1s 一次（原先每个入站帧都全表 removeIf）。
- `ChannelClient.call` 的两条 IPC 日志从 `info` 降为 `debug` 且仅在开关打开时拼字符串。

**版本**：versionCode 22→23，versionName 1.9.1→1.9.2，CHANGELOG 顶部新增 v1.9.2 分节。

### 第四轮第四批：给 IpcCodec 补上可执行的验证（同日）
- 新建 `tools/verify-ipc-codec/`（`run.sh` + `CodecVerify.kt`）。**关键手法**：
  `IpcCodec.kt` 只依赖 kotlin-stdlib + gson、无任何 Android API，所以可以脱离 Android
  直接跑 —— 用 Gradle 缓存里已有的 `kotlin-compiler-embeddable` 编译成 class 再
  `java -cp` 执行，不需要模拟器、不需要给 app 模块加测试依赖、不需要联网。
  编译器版本从 `gradle/libs.versions.toml` 的 `kotlin` 字段取。
- **踩坑 1**：Git Bash/MSYS **不会**把 POSIX 路径（`/c/Users/...`）转成 Windows 路径传给
  `java`，直接拼进 `-cp` 会 ClassNotFoundException。必须过一遍 `cygpath -w`。
- **踩坑 2**：`${TMPDIR:-/tmp}` 在 Windows 下 TMPDIR 是 `C:/...` 形式，拼进 bash 路径会
  变成相对路径、并触发沙箱的 `rm -rf` 安全拦截。改用 `mktemp -d` 且不做删除。
- 结果：60 项断言全部通过。核心是证明**新旧实现在字节层面等价**（varint 全边界值逐字节
  一致、整帧布局与手工拼装一致），以及负长度 varint 不再抛 NegativeArraySizeException。

### 第四轮第六批：缓存清理页的两个致命 bug（同日，编译已验证）
重点是 `CacheCleanScreen`。两个 bug 互相掩盖 —— **单独修任何一个都会出事**。

1. **「清理」按钮是空操作**。回调里先 `selectedIds = emptySet()`，再在协程里
   `if (item.id in selectedIds) item.clean(ctx)` → 读到空集合，**一个字节都没删**。
   界面照样转圈 + 提示"已完成"。修复：进协程前先 `val toClean = selectedIds` 快照。
2. **修好按钮后会立刻抹掉所有已配对设备**。有个清理项递归删整个 `filesDir`：
   `filesDir.listFiles()?.forEach { it.deleteRecursively() }`。
   而 `filesDir/datastore/zemote_settings.preferences_pb` 是 DataStore 文件 ——
   **AccountStore 把全部已配对设备（Keystore 加密后的配对 URL）存在那里**，
   ThemeManager 主题设置也在同一文件。该项在界面上叫「应用数据文件 / 本地持久化数据文件」，
   有勾选框 + 红色清理按钮，**没有二次确认**。
   修复：改为只清理崩溃报告（filesDir 里唯一可安全删的），走 `CrashHandler.clear()`；
   字符串换 `cache_crash_report`。代码里留了醒目注释。
   **因果**：清理从没真正执行过 → 数据丢失路径从未触发 → 所以一直没被发现。
3. `AccountStore.load()` 非幂等：AccountsScreen 在 AnimatedContent 里，切 Tab 会重组并
   重跑 LaunchedEffect → 每次切 Tab 都重做「DataStore 读 + JSON 解析 + N 次 Keystore 解密」。
   加 `loadedOnce` 守卫 + `force` 参数。
4. `applyDeltas` 末尾加安全网：本轮结束若 `pendingDeltas` 非空就 `scheduleDeltaFlush()`，
   覆盖"delta 先到、行由 row.upserted 补进来、之后无 delta"导致文本卡住不显示的路径。

**审计过确认无问题的**：`CredentialCipher`（AES/GCM + 12 字节 IV 前缀 + base64url，正确；
调用方都在 `withContext(Dispatchers.IO)` 内，不会阻塞主线程）、`AccountStore` 读写调度、
`LanguagePrefs`（attachBaseContext 同步读是刻意取舍）。`AccountStore.touch()` 全仓无调用（保留）。

**教训（值得记）**：改"清理/删除"这类功能时，必须同时检查
(a) 选择集/快照是否在异步前取好，(b) 删除范围是否包含了不该删的持久化数据
（DataStore 落在 `filesDir/datastore/`，很容易被"清空 filesDir"这类写法误伤）。

### 第四轮第七批：模拟器冒烟验证（同日）
在 `Medium_Phone` AVD 上实装了本次构建（headless: `-no-window -gpu swiftshader_indirect`）。
- ✅ 安装成功、启动成功（冷启动 TotalTime 9743ms）、**无崩溃**（crash buffer + FATAL 过滤均空）
- ⚠️ 系统弹出「Android 应用兼容性」对话框拦截 UI，缓存清理页没点到 —— 该项仍只有编译级验证。

**🔶 发现待处理问题：原生库不符合 16KB 页对齐**。系统弹窗列出：
`libimage_processing_util_jni.so`（CameraX）、`libdatastore_shared_counter.so`（DataStore）、
`libandroidx.graphics.path.so`（Compose）。三者都来自依赖库，不是本项目编译的。
影响：16KB 页设备（部分 Android 15+）以兼容模式运行；Play 新提交已要求支持。
**注意**：`app/build.gradle.kts` 里 `jniLibs { useLegacyPackaging = true }` 的注释写着
"确保 16KB 页面对齐兼容"，实测并未达成 —— 注释与事实不符。
对齐由 `.so` 自身 ELF LOAD 段的构建参数（`-Wl,-z,max-page-size=16384`）决定，打包方式解决不了。
建议：升级 camera / datastore / compose 到提供 16KB 对齐产物的版本后重验。

**环境经验（重要）**：
1. **模拟器活不过工具调用边界** —— 它是后台任务 shell 的子进程，任务一结束就被回收。
   要跑冒烟验证必须把「启动→安装→操作→截图→关模拟器」全部放进**同一个**后台命令，
   并在 `trap EXIT` 里 `adb emu kill`。
2. `adb` 是 Windows 二进制，**必须 `cygpath -w` 转换 APK 路径**，否则
   `failed to stat /c/Users/...`（第一次踩了这个坑，装的是旧版本还以为验证过了）。
3. `uiautomator dump` 拿真实控件坐标比猜坐标可靠；但系统级弹窗会把它挡住。
4. `-no-window` 下 `screencap` 仍能正常截图。
